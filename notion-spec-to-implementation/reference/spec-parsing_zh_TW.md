# 規格書解析 (Specification Parsing)

## 尋找規格書

在開始解析前，請先定位規格書頁面：

```
1. 搜尋規格書：
   Notion:notion-search
   query: "[功能名稱] 規格書" 或 "[功能名稱] 規格"
   
2. 處理結果：
   - 若找到 → 使用頁面網址/ID。
   - 若有多個 → 詢問使用者要使用哪一個。
   - 若未找到 → 向使用者索取網址/ID。

範例：
Notion:notion-search
query: "使用者個人資料 API 規格書"
query_type: "internal"
```

## 閱讀規格書

找到規格書後，使用 `Notion:notion-fetch` 獲取內容：

1. 閱讀完整內容。
2. 識別關鍵章節。
3. 擷取結構化資訊。
4. 註記模糊處或資訊缺口。

```
Notion:notion-fetch
id: "搜尋到的規格書頁面 ID"
```

## 常見的規格書結構

### 以需求為導向的規格書 (Requirements-Based Spec)

```
# 功能規格書
## 概覽
[功能描述]

## 需求 (Requirements)
### 功能性需求
- REQ-1：[需求描述]
- REQ-2：[需求描述]

### 非功能性需求
- PERF-1：[效能需求]
- SEC-1：[安全性需求]

## 驗收標準 (Acceptance Criteria)
- AC-1：[標準描述]
- AC-2：[標準描述]
```

擷取要點：
- 功能性需求清單。
- 非功能性需求清單。
- 驗收標準清單。

### 以使用者故事為導向的規格書 (User Story Based Spec)

```
# 功能規格書
## 使用者故事 (User Stories)
### 身為 [使用者類型]
我想要 [目標]
以便於 [效益]

**驗收標準**：
- [標準描述]
- [標準描述]
```

擷取要點：
- 使用者畫像 (Personas)。
- 需要的目標/能力。
- 每個故事對應的驗收標準。

### 技術設計文件 (Technical Design Doc)

```
# 技術設計文件
## 問題陳述
[問題描述]

## 建議解決方案
[處理解法]

## 架構設計
[架構細節]

## 實作計畫
[實作方式]
```

擷取要點：
- 待解決的問題。
- 提議的解決方案。
- 架構決策。
- 實作指引。

### 產品需求文件 (PRD)

```
# PRD：[功能名稱]
## 目標
[業務目標]

## 使用者需求
[待解決的使用者問題]

## 功能清單
[功能列表]

## 成功指標
[如何衡量成功]
```

擷取要點：
- 業務目標。
- 使用者需求。
- 功能清單。
- 成功指標。

## 擷取策略 (Extraction Strategies)

### 需求識別

尋找以下關鍵字：
- 「必須 (Must)」、「應該 (Should)」、「將要 (Will)」等陳述。
- 編號需求（如 REQ-1 等）。
- 使用者故事（身為... 我想要...）。
- 驗收標準章節。
- 功能清單。

### 分類方式

按以下類別對需求進行分組：

**功能性需求 (Functional)**：系統要做什麼
- 使用者能力。
- 系統行為。
- 數據操作。

**非功能性需求 (Non-Functional)**：系統表現如何
- 效能目標。
- 安全性要求。
- 可擴展性需求。
- 可用性要求。
- 合規性要求。

**限制條件 (Constraints)**：限制因素
- 技術限制。
- 業務限制。
- 時程限制。

### 優先級擷取

識別優先級指標：
- 「緊急 (Critical)」、「必備 (Must have)」、「P0」。
- 「重要 (Important)」、「應該有 (Should have)」、「P1」。
- 「加分 (Nice to have)」、「可以有 (Could have)」、「P2」。
- 「未來 (Future)」、「暫不執行 (Won't have)」、「P3」。

根據優先級將其對映至不同的實作階段。

## 處理模糊性 (Handling Ambiguity)

### 不明確的需求

當需求具備歧義時：

```markdown
## 需要釐清的事項 (Clarifications Needed)

### [需求 ID/描述]
**目前文本**："[模糊的需求描述]"
**問題**：[需要釐清的部分]
**影響**：[這對實作有何影響]
**目前假設**：[若有，請列出目前的暫時假設]
```

建立釐清任務或在規格書中新增評論。

### 資訊缺失

當缺失關鍵資訊時：

```markdown
## 資訊缺失 (Missing Information)

- **[主題]**：規格書未指定 [缺失的內容]
- **影響**：阻礙了 [受影響的任務]
- **行動**：需要 [如何解決]
```

### 矛盾的需求

當需求相互衝突時：

```markdown
## 矛盾的需求 (Conflicting Requirements)

**衝突點**：REQ-1 提到 [X]，但 REQ-5 提到 [Y]
**影響**：[對實作的影響]
**需要解決**：[需要做出的決策]
```

## 驗收標準解析

### 顯性標準 (Explicit Criteria)

直接列出的驗收標準：

```
## 驗收標準
- 使用者可以使用電子郵件與密碼登入
- 系統發送確認信
- 環節 (Session) 在 24 小時後過期
```

轉換為檢查清單：
- [ ] 使用者可以使用電子郵件與密碼登入。
- [ ] 系統發送確認信。
- [ ] 環節 (Session) 在 24 小時後過期。

### 隱含標準 (Implicit Criteria)

從需求中推導：

```
需求：「使用者可以上傳最大 100MB 的檔案」

隱含的驗收標準：
- [ ] 100MB 以內的檔案上傳成功。
- [ ] 超過 100MB 的檔案被拒絕並顯示錯誤訊息。
- [ ] 上傳期間顯示進度指示器。
- [ ] 上傳可以被取消。
```

### 可測試的標準

確保標準是可測試的：

❌ **不可測試**：「系統很快」
✓ **可測試**：「頁面載入時間 < 2 秒」

❌ **不可測試**：「使用者喜歡這個介面」
✓ **可測試**：「90% 的測試使用者能成功完成任務」

## 技術細節擷取

### 架構資訊

擷取：
- 系統組件。
- 數據模型。
- API/介面。
- 整合點。
- 技術選型。

### 設計決策

註記：
- 技術選擇。
- 架構模式。
- 曾做的權衡。
- 提供的理由。

### 實作指引

尋找：
- 建議的方法。
- 程式碼範例。
- 推薦的函式庫。
- 提及的最佳實踐。

## 依賴關係識別

### 外部依賴

從規格書中識別：
- 需要的第三方服務。
- 需要的外部 API。
- 基礎設施要求。
- 工具/函式庫依賴。

### 內部依賴

識別：
- 需要優先完成的其他功能。
- 需要的共用組件。
- 跨團隊依賴。
- 數據依賴。

### 時程依賴

註記：
- 硬性截止日期。
- 里程碑依賴。
- 執行順序要求。

## 範圍擷取 (Scope Extraction)

### 範圍內 (In Scope)

明確包含的內容：
- 要建構的功能。
- 要支援的使用案例。
- 要服務的使用者/畫像。

### 範圍外 (Out of Scope)

明確排除的內容：
- 推遲的功能。
- 不支援的使用案例。
- 不處理的邊緣案例。

### 假設事項 (Assumptions)

假設的情況：
- 環境假設。
- 使用者行為假設。
- 系統狀態假設。

## 風險識別

擷取風險資訊：

### 技術風險
- 未經證實的技術。
- 複雜的整合。
- 效能疑慮。
- 擴展性未知數。

### 業務風險
- 市場時機。
- 資源可用性。
- 對他人的依賴。

### 緩解策略 (Mitigation Strategies)

註記規格書中提到的任何緩解方法。

## 規格書品質評估

評估規格書的完整性：

✓ **優質規格書**：
- 需求清晰。
- 驗收標準明確。
- 定義了優先級。
- 已識別風險。
- 概述了技術方法。

⚠️ **不完整的規格書**：
- 需求模糊。
- 缺少驗收標準。
- 優先級不明確。
- 缺少風險分析。
- 缺乏技術細節。

記錄缺口並建立釐清任務。
