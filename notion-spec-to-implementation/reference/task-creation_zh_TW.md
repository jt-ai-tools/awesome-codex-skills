# 從規格書建立任務 (Task Creation from Specs)

## 尋找任務資料庫

在建立任務之前，先定位任務資料庫：

```
1. 搜尋任務資料庫：
   Notion:notion-search
   query: "任務" 或 "任務管理" 或 "[專案名稱] 任務"
   
2. 獲取資料庫結構綱要：
   Notion:notion-fetch
   id: "搜尋到的資料庫 ID"
   
3. 識別數據源：
   - 尋找 <data-source url="collection://..."> 標籤。
   - 擷取 Collection ID 以作為 parent 參數使用。
   
4. 註記結構綱要：
   - 必填屬性。
   - 屬性型別與選項。
   - 用於連結的關聯 (Relation) 屬性。

範例：
Notion:notion-search
query: "工程任務"
query_type: "internal"

Notion:notion-fetch
id: "tasks-database-id"
```

結果：`collection://abc-123-def` 可用作父層 (Parent)。

## 任務拆解策略

### 規模指引 (Size Guidelines)

**理想的任務規模**：
- 可在 1-2 天內完成。
- 單一且清晰的交付物。
- 可獨立測試。
- 依賴關係極少。

**過大的任務**：
- 耗時超過 3 天。
- 多個交付物。
- 依賴關係過多。
- 應進一步拆解。

**過小的任務**：
- 耗時小於 2 小時。
- 過於瑣碎。
- 應與相關工作合併。

### 按階段劃分的細緻度

**初期階段**：可接受較大的任務。
- 「設計資料庫結構綱要」。
- 「建立 API 結構」。

**中期階段**：中等規模任務。
- 「實作使用者認證」。
- 「建置儀表板 UI」。

**後期階段**：較小且精確的任務。
- 「修復表單中的驗證 Bug」。
- 「為按鈕新增載入中狀態」。

## 任務建立模式

針對每項需求或工作項目：

```
1. 識別工作內容
2. 確定任務規模
3. 在資料庫中建立任務
4. 設定屬性
5. 撰寫任務描述
6. 連結至規格書/計畫
```

### 建立任務

```
使用 Notion:notion-create-pages：

parent: {
  type: "data_source_id",
  data_source_id: "collection://tasks-db-uuid"
}

properties: {
  "[標題屬性]": "任務：[清晰的任務名稱]",
  "狀態": "待處理",
  "優先級": "[高/中/低]",
  "[專案/相關項目]": ["規格書頁面 ID", "計畫頁面 ID"],
  "負責人": "[人員]"（若已知）,
  "date:到期日:start": "[日期]"（若適用）,
  "date:到期日:is_datetime": 0
}

content: "[使用模板撰寫的任務描述]"
```

## 任務類型 (Task Types)

### 基礎設施/設定任務

```
標題：「設定：[設定內容]」
範例：
- 「設定：配置資料庫連線池」
- 「設定：初始化認證中間件」
- 「設定：建立 CI/CD 管線」

重點：讓環境與工具就緒。
```

### 功能實作任務

```
標題：「實作：[功能名稱]」
範例：
- 「實作：使用者登入流程」
- 「實作：檔案上傳功能」
- 「實作：儀表板小工具」

重點：建置特定功能。
```

### 整合任務

```
標題：「整合：[整合內容]」
範例：
- 「整合：將前端連線至 API」
- 「整合：串接支付服務商」
- 「整合：將個人資料連結至儀表板」

重點：連接各個組件。
```

### 測試任務

```
標題：「測試：[測試內容]」
範例：
- 「測試：撰寫認證服務的單元測試」
- 「測試：結帳流程的 E2E 測試」
- 「測試：API 的效能測試」

重點：驗證與品質保證。
```

### 文件任務

```
標題：「文件：[文件內容]」
範例：
- 「文件：API 端點說明」
- 「文件：環境設定指南」
- 「文件：架構決策紀錄」

重點：建立技術文件。
```

### Bug 修復任務

```
標題：「修復：[Bug 描述]」
範例：
- 「修復：Safari 上的登入錯誤」
- 「修復：圖像處理中的記憶體洩漏」
- 「修復：支付流程中的競態條件」

重點：解決現有問題。
```

### 重構任務

```
標題：「重構：[重構內容]」
範例：
- 「重構：將認證邏輯擷取至服務層」
- 「重構：優化資料庫查詢」
- 「重構：簡化組件層級」

重點：提升程式碼品質。
```

## 任務排序 (Sequencing Tasks)

### 關鍵路徑 (Critical Path)

識別必須最先發生的任務：

```
1. 資料庫結構綱要
2. API 基礎建設
3. 核心商業邏輯
4. 前端整合
5. 測試驗證
6. 部署
```

### 並行軌道 (Parallel Tracks)

可以同時進行的任務：

```
軌道 A：後端開發
- API 端點
- 商業邏輯
- 資料庫操作

軌道 B：前端開發
- UI 組件
- 狀態管理
- 路由設定

軌道 C：基礎設施
- CI/CD 設定
- 監控機制
- 技術文件
```

### 按階段排序

按實作階段進行分組：

```
第 1 階段（基礎）：
- 設定任務
- 基礎設施任務

第 2 階段（核心）：
- 功能實作任務
- 整合任務

第 3 階段（精煉）：
- 測試任務
- 文件任務
- 優化任務
```

## 優先級指派 (Priority Assignment)

### P0/緊急 (Critical)
- 阻礙所有其他工作。
- 核心功能。
- 安全性要求。
- 數據完整性。

### P1/高 (High)
- 重要功能。
- 面向使用者的功能。
- 效能要求。

### P2/中 (Medium)
- 加分功能。
- 優化項。
- 微小改進。

### P3/低 (Low)
- 未來增強項。
- 邊緣案例處理。
- 視覺優化。

## 預估 (Estimation)

### 故事點數 (Story Points)

若使用故事點數：
- 1 點：數小時。
- 2 點：半天。
- 3 點：一整天。
- 5 點：2 天。
- 8 點：3-4 天（考慮進一步拆解）。

### 時間預估

直接時間估計：
- 2-4 小時：小任務。
- 1 天：中任務。
- 2 天：大任務。
- 3 天以上：必須拆解。

### 預估考量因素

考慮：
- 複雜度。
- 未知事項。
- 依賴關係。
- 測試需求。
- 文件需求。

## 任務關係 (Task Relationships)

### 父任務模式 (Parent Task Pattern)

針對大型功能：

```
父任務：「功能：使用者認證」
子任務：
- 「設定：配置認證程式庫」
- 「實作：登入流程」
- 「實作：密碼重設」
- 「測試：認證功能」
```

### 依賴鏈模式 (Dependency Chain Pattern)

針對順序性工作：

```
任務 A：「設計資料庫結構綱要」
↓（阻礙）
任務 B：「實作數據模型」
↓（阻礙）
任務 C：「建立 API 端點」
↓（阻礙）
任務 D：「與前端整合」
```

### 相關任務模式 (Related Tasks Pattern)

針對並行工作：

```
核心項目：「功能：儀表板」
相關項目：
- 「儀表板數據的後端 API」
- 「前端儀表板組件」
- 「儀表板數據快取」
```

## 批量建立任務 (Bulk Task Creation)

當需要建立許多任務時：

```
針對拆解後的每個工作項：
  1. 確定任務屬性。
  2. 建立任務頁面。
  3. 連結至規格書/計畫。
  4. 設定關聯性。

隨後：
  1. 在計畫中更新任務連結。
  2. 審查排序。
  3. 指派任務（若已知）。
```

## 任務命名慣例

**要具體**：
✓ 「實作使用電子郵件/密碼的使用者登入」
✗ 「新增登入」

**包含上下文**：
✓ 「儀表板：新增營收圖表小工具」
✗ 「新增圖表」

**使用行動動詞**：
- 實作 (Implement)、建置 (Build)、建立 (Create)
- 整合 (Integrate)、連接 (Connect)、連結 (Link)
- 修復 (Fix)、解決 (Resolve)、偵錯 (Debug)
- 測試 (Test)、驗證 (Validate / Verify)
- 文件化 (Document)、撰寫 (Write)、更新 (Update)
- 重構 (Refactor)、優化 (Optimize)、改進 (Improve)
