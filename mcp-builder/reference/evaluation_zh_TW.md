# MCP 伺服器評估指南 (MCP Server Evaluation Guide)

## 概覽 (Overview)

本文件為建立 MCP 伺服器的綜合評估提供指引。評估旨在測試 LLM 能否僅使用提供的工具，有效地利用您的 MCP 伺服器來回答現實且複雜的問題。

---

## 快速參考

### 評估要求
- 建立 10 個人類可讀的問題。
- 問題必須是「唯讀」、「獨立」且「非破壞性」的。
- 每個問題應需要多次工具調用（可能多達數十次）。
- 答案必須是單一且可驗證的數值/字串。
- 答案必須是穩定 (STABLE) 的（不會隨時間改變）。

### 輸出格式
```xml
<evaluation>
   <qa_pair>
      <question>您的問題在此</question>
      <answer>單一可驗證的答案</answer>
   </qa_pair>
</evaluation>
```

---

## 評估的目的

衡量 MCP 伺服器品質的標準**不**在於伺服器實作工具的程度或全面性，而在於這些實作（輸入/輸出結構綱要、文件字串/描述、功能性）能否讓在沒有其他背景資訊且**僅**能存取 MCP 伺服器的情況下的 LLM，回答現實且困難的問題。

## 評估概覽

建立 10 個人類可讀的問題，且僅需透過「唯讀」、「獨立」、「非破壞性」及「冪等 (IDEMPOTENT)」的操作即可回答。每個問題應具備以下特性：
- 現實性
- 清晰且簡潔
- 無歧義
- 複雜度高，可能需要數十次工具調用或步驟
- 可透過您預先確定的單一可驗證值來回答

## 問題編寫準則

### 核心要求

1. **問題必須相互獨立**
   - 每個問題都不應依賴於任何其他問題的答案。
   - 不應假設處理另一個問題時先前執行的寫入操作。

2. **問題必須僅需使用「非破壞性」且「冪等」的工具**
   - 不應指示或要求修改狀態以獲得正確答案。

3. **問題必須具備現實性、清晰、簡潔且複雜**
   - 必須需要另一個 LLM 使用多個（可能數十個）工具或步驟來回答。

### 複雜度與深度

4. **問題必須需要深度探索**
   - 考慮需要多個子問題與順序性工具調用的「多跳 (Multi-hop)」問題。
   - 每個步驟都應能從前一個問題中發現的資訊中獲益。

5. **問題可能需要大量分頁 (Paging)**
   - 可能需要翻閱多頁結果。
   - 可能需要查詢舊數據（例如過期 1-2 年的數據）以尋找小眾資訊。
   - 問題必須具有「難度」。

6. **問題必須需要深度理解**
   - 而非僅止於表面知識。
   - 可以將複雜想法轉化為需要證據支持的是非題 (True/False)。
   - 可以使用選擇題格式，讓 LLM 必須搜尋不同的假設。

7. **問題不應能透過簡單的關鍵字搜尋解決**
   - 不要包含目標內容中的特定關鍵字。
   - 使用同義詞、相關概念或改寫。
   - 需要多次搜尋、分析多個相關項、擷取上下文，最後推導出答案。

### 工具測試

8. **問題應對工具的傳回值進行壓力測試**
   - 可以誘導工具回傳大型 JSON 物件或清單，使 LLM 負載過重。
   - 應需要理解多種型態的數據：
     - ID 與名稱
     - 時間戳記與日期時間（月、日、年、秒）
     - 檔案 ID、名稱、擴充功能與 MIME 類型
     - URL、GID 等
   - 應探查工具回傳所有有用數據形式的能力。

9. **問題應主要反映真實的人類使用案例**
   - 即在 LLM 輔助下的人類會關心的資訊檢索任務。

10. **問題可能需要數十次工具調用**
    - 這對上下文有限的 LLM 構成挑戰。
    - 鼓勵 MCP 伺服器工具減少回傳的資訊量。

11. **包含具備歧義的問題**
    - 可能是問題本身具歧義，或者需要針對調用哪些工具做出困難決策。
    - 強制 LLM 可能犯錯或誤解。
    - 確保儘管存在「歧義」，但**仍然存在單一可驗證的答案**。

### 穩定性

12. **問題設計必須確保答案「不會改變」**
    - 不要詢問依賴於動態「當前狀態」的問題。
    - 例如，不要計算：
      - 貼文的反應 (Reactions) 數量
      - 討論串的回覆數量
      - 頻道中的成員數量

13. **不要讓 MCP 伺服器限制您建立問題的類型**
    - 建立具挑戰性且複雜的問題。
    - 某些問題可能無法透過現有的 MCP 伺服器工具解決。
    - 問題可能需要特定的輸出格式（日期時間 vs. Epoch 時間，JSON vs. MARKDOWN）。
    - 問題可能需要數十次工具調用才能完成。

## 答案編寫準則

### 驗證

1. **答案必須能透過「直接字串比對」來驗證**
   - 如果答案可以用多種格式書寫，請在「問題」中明確指定輸出格式。
   - 範例：「使用 YYYY/MM/DD 格式。」、「回覆 True 或 False。」、「僅回答 A, B, C 或 D，不加其他內容。」
   - 答案應為單一「可驗證的值」，例如：
     - 使用者 ID、使用者名稱、顯示名稱、名字、姓氏
     - 頻道 ID、頻道名稱
     - 訊息 ID、字串
     - URL、標題
     - 數值數量
     - 時間戳記、日期時間
     - 布林值 (適用於是非題)
     - 電子郵件地址、電話號碼
     - 檔案 ID、檔案名稱、副檔名
     - 選擇題答案
   - 答案不應需要特殊格式或複雜的結構化輸出。
   - 答案將使用**直接字串比對**進行驗證。

### 可讀性

2. **答案應優先選擇「人類可讀」的格式**
   - 範例：姓名、名字、姓氏、日期時間、檔案名稱、訊息字串、URL、yes/no、true/false、a/b/c/d。
   - 而非不透明的 ID（雖然 ID 也是可以接受的）。
   - 絕大多數答案應為人類可讀。

### 穩定性

3. **答案必須是穩定/靜態的 (STABLE/STATIONARY)**
   - 觀察舊內容（例如：已結束的對話、已發布的專案、已回答的問題）。
   - 根據「已關閉」的概念建立問題，這些概念將始終回傳相同的答案。
   - 問題可以要求考慮固定的時間視窗，以隔絕動態答案的影響。
   - 依賴不太可能改變的背景資訊。
   - 範例：如果尋找論文名稱，請確保描述足夠「具體」，使答案不會與後來發表的論文混淆。

4. **答案必須清晰且無歧義**
   - 問題設計必須確保存在唯一的、清晰的答案。
   - 答案可以透過使用 MCP 伺服器工具推導出來。

### 多樣性

5. **答案必須多樣化**
   - 答案應為多種型態與格式的單一可驗證值。
   - 使用者概念：使用者 ID、使用者名稱、顯示名稱、名字、姓氏、電子郵件地址、電話號碼。
   - 頻道概念：頻道 ID、頻道名稱、頻道主題。
   - 訊息概念：訊息 ID、訊息字串、時間戳記、月、日、年。

6. **答案不得為複雜結構**
   - 不是數值列表。
   - 不是複雜物件。
   - 不是 ID 或字串的列表。
   - 不是自然語言文本。
   - **除非**該答案能輕易地透過「直接字串比對」進行驗證。
   - 且能被現實地重現。
   - LLM 應該不太可能以任何其他順序或格式回傳相同的列表。

## 評估流程

### 步驟 1：文件檢查

閱讀目標 API 的文件以瞭解：
- 可用的端點與功能。
- 如果存在歧義，請從網頁獲取額外資訊。
- **盡可能並行化**執行此步驟。
- 確保每個子代理人僅檢查來自檔案系統或網頁的文件。

### 步驟 2：工具檢查

列出 MCP 伺服器中可用的工具：
- 直接檢查 MCP 伺服器。
- 理解輸入/輸出結構綱要、文件字串與描述。
- 此階段**不要**直接調用工具。

### 步驟 3：建立理解

重複步驟 1 與 2，直到您有充分的理解：
- 多次迭代。
- 思考您想要建立的任務類型。
- 精煉您的理解。
- 在任何階段都不應閱讀 MCP 伺服器實作本身的程式碼。
- 利用您的直覺與理解力來建立合理、現實但「非常有挑戰性」的任務。

### 步驟 4：唯讀內容檢查

在理解 API 與工具後，使用 MCP 伺服器工具：
- 僅使用「唯讀」且「非破壞性」的操作來檢查內容。
- 目標：識別具體內容（例如：使用者、頻道、訊息、專案、任務）以建立現實的問題。
- 不應調用任何修改狀態的工具。
- 不會閱讀 MCP 伺服器實作本身的程式碼。
- 讓個別子代理人進行獨立探索以並行化此步驟。
- 確保每個子代理人僅執行「唯讀」、「非破壞性」且「冪等」的操作。
- **請注意**：某些工具可能會回傳大量數據，導致您用完上下文空間。
- 進行「遞增的、小型的且具針對性」的工具調用以進行探索。
- 在所有工具調用請求中，使用 `limit` 參數限制結果數量 (<10)。
- 使用分頁功能。

### 步驟 5：任務生成

在檢查內容後，建立 10 個人類可讀的問題：
- LLM 應能透過 MCP 伺服器回答這些問題。
- 遵循上述所有關於問題與答案的準則。

## 輸出格式

每個 QA 對由一個問題與一個答案組成。輸出應為具備此結構的 XML 檔案：

```xml
<evaluation>
   <qa_pair>
      <question>找出 2024 年第二季建立且已完成任務數量最多的專案。請問該專案名稱為何？</question>
      <answer>網站重新設計 (Website Redesign)</answer>
   </qa_pair>
   <qa_pair>
      <question>搜尋標籤為 "bug" 且在 2024 年 3 月關閉的任務。哪位使用者關閉的任務最多？請提供其使用者名稱。</question>
      <answer>sarah_dev</answer>
   </qa_pair>
   <qa_pair>
      <question>尋找修改了 /api 目錄中檔案且在 2024 年 1 月 1 日至 1 月 31 日之間合併的 Pull Request。請問有多少位不同的貢獻者參與了這些 PR？</question>
      <answer>7</answer>
   </qa_pair>
   <qa_pair>
      <question>找出在 2023 年之前建立且獲得最多星數 (Stars) 的儲存庫。請問該儲存庫名稱為何？</question>
      <answer>data-pipeline</answer>
   </qa_pair>
</evaluation>
```

## 評估範例

### 良好的問題範例

**範例 1：需要深度探索的多跳問題 (GitHub MCP)**
```xml
<qa_pair>
   <question>尋找在 2023 年第三季被封存 (Archived)，且先前曾是組織中被分叉 (Forked) 次數最多的專案。請問該儲存庫使用的主要程式語言是什麼？</question>
   <answer>Python</answer>
</qa_pair>
```

此問題良好之處：
- 需要多次搜尋才能找到已封存的儲存庫。
- 需要識別哪一個在封存前擁有最多分叉數。
- 需要檢查儲存庫詳情以獲取語言資訊。
- 答案是一個簡單且可驗證的值。
- 基於不會改變的歷史（已關閉）數據。

**範例 2：需要理解上下文而非關鍵字匹配 (專案管理 MCP)**
```xml
<qa_pair>
   <question>定位在 2023 年底完成的關於優化客戶入職流程 (Customer Onboarding) 的專案。專案負責人在完成後建立了一份回顧文件。請問該負責人當時的職稱是什麼？</question>
   <answer>產品經理 (Product Manager)</answer>
</qa_pair>
```

此問題良好之處：
- 未使用具體的專案名稱（「關於優化客戶入職流程的專案」）。
- 需要尋找特定時間範圍內完成的專案。
- 需要識別專案負責人及其職稱。
- 需要理解回顧文件中的背景資訊。
- 答案是人類可讀且穩定的。
- 基於已完成的工作（不會改變）。

**範例 3：需要多個步驟的複雜聚合 (任務追蹤 MCP)**
```xml
<qa_pair>
   <question>在 2024 年 1 月回報且被標記為最高優先級 (Critical) 的所有 Bug 中，哪位受指派者在 48 小時內解決了其受指派 Bug 的比例最高？請提供該使用者的使用者名稱。</question>
   <answer>alex_eng</answer>
</qa_pair>
```

此問題良好之處：
- 需要按日期、優先級與狀態過濾 Bug。
- 需要按受指派者分組並計算解決率。
- 需要理解時間戳記以確定 48 小時的時間視窗。
- 測試了分頁功能（可能需要處理大量 Bug）。
- 答案是單一的使用者名稱。
- 基於特定時期的歷史數據。

**範例 4：需要跨多種數據類型進行整合 (CRM MCP)**
```xml
<qa_pair>
   <question>尋找在 2023 年第四季從 Starter 方案升級到 Enterprise 方案且年度合約價值 (ACV) 最高的帳戶。請問該帳戶所屬的行業為何？</question>
   <answer>醫療保健 (Healthcare)</answer>
</qa_pair>
```

此問題良好之處：
- 需要理解訂閱等級的變更。
- 需要識別特定時段內的升級事件。
- 需要比較合約價值。
- 必須存取帳戶的行業資訊。
- 答案簡單且可驗證。
- 基於已完成的歷史交易。

### 不良的問題範例

**範例 1：答案會隨時間改變**
```xml
<qa_pair>
   <question>目前指派給工程團隊的開啟任務有多少個？</question>
   <answer>47</answer>
</qa_pair>
```

此問題不良之處：
- 隨著任務的建立、關閉或重新指派，答案將會改變。
- 並非基於穩定/靜態的數據。
- 依賴於動態的「當前狀態」。

**範例 2：透過關鍵字搜尋太容易解決**
```xml
<qa_pair>
   <question>尋找標題為 "Add authentication feature" 的 Pull Request 並告訴我誰建立了它。</question>
   <answer>developer123</answer>
</qa_pair>
```

此問題不良之處：
- 透過精確標題的關鍵字搜尋即可輕易解決。
- 不需要深度的探索或理解。
- 不需要整合或分析。

**範例 3：答案格式具歧義**
```xml
<qa_pair>
   <question>列出所有以 Python 為主要語言的儲存庫。</question>
   <answer>repo1, repo2, repo3, data-pipeline, ml-tools</answer>
</qa_pair>
```

此問題不良之處：
- 答案是一個清單，可能以任何順序回傳。
- 難以透過直接字串比對進行驗證。
- LLM 的格式化方式可能不同（JSON 陣列、逗號分隔、換行分隔）。
- 最好改為詢問特定的聚合值（數量）或最高級（例如星數最多者）。

## 驗證流程

建立評估後：

1. **檢查 XML 檔案**以理解其結構綱要 (Schema)。
2. **載入每個任務指令**，並並行使用 MCP 伺服器與工具，透過嘗試親自解決任務來確定正確答案。
3. **標記任何需要執行寫入或破壞性操作**的步驟。
4. **彙總所有正確答案**並替換文件中任何不正確的答案。
5. **移除任何需要寫入或破壞性操作**的 `<qa_pair>`。

記得並行解決任務以避免用完上下文空間，最後再彙總所有答案並對檔案進行變更。

## 建立高品質評估的提示

1. 在生成任務之前**深入思考並預先規劃**。
2. **在有機會時並行化**以加速過程並管理上下文。
3. **專注於現實的使用案例**，即人類實際想要完成的任務。
4. **建立具挑戰性的問題**，以測試 MCP 伺服器功能的極限。
5. 透過使用歷史數據與已關閉的概念來**確保穩定性**。
6. 透過使用 MCP 伺服器工具親自解決問題來**驗證答案**。
7. 根據過程中的學習進行**迭代與精煉**。

# 執行評估

建立評估檔案後，您可以使用提供的評估工具包來測試您的 MCP 伺服器。

## 設定

1. **安裝依賴項**

   ```bash
   pip install -r scripts/requirements.txt
   ```

   或者手動安裝：
   ```bash
   pip install openai mcp
   ```

2. **設定 API 金鑰**

   ```bash
   export OPENAI_API_KEY=您的金鑰在此
   ```

## 評估檔案格式

評估檔案使用 XML 格式，包含 `<qa_pair>` 元素：

```xml
<evaluation>
   <qa_pair>
      <question>找出 2024 年第二季建立且已完成任務數量最多的專案。請問該專案名稱為何？</question>
      <answer>網站重新設計 (Website Redesign)</answer>
   </qa_pair>
   <qa_pair>
      <question>搜尋標籤為 "bug" 且在 2024 年 3 月關閉的任務。哪位使用者關閉的任務最多？請提供其使用者名稱。</question>
      <answer>sarah_dev</answer>
   </qa_pair>
</evaluation>
```

## 執行評估

評估腳本 (`scripts/evaluation.py`) 支援三種傳輸類型：

**重要提示：**
- **stdio 傳輸**：評估腳本會自動為您啟動並管理 MCP 伺服器程序。**不要**手動執行伺服器。
- **sse/http 傳輸**：在執行評估之前，您必須**先**啟動 MCP 伺服器。腳本將連線到指定 URL 上已在執行的伺服器。

### 1. 本地 STDIO 伺服器

適用於本地執行的 MCP 伺服器（腳本會自動啟動伺服器）：

```bash
python scripts/evaluation.py 
  -t stdio 
  -c python 
  -a my_mcp_server.py 
  evaluation.xml
```

帶有環境變數：
```bash
python scripts/evaluation.py 
  -t stdio 
  -c python 
  -a my_mcp_server.py 
  -e API_KEY=abc123 
  -e DEBUG=true 
  evaluation.xml
```

### 2. 伺服器傳送事件 (SSE)

適用於基於 SSE 的 MCP 伺服器（您必須先啟動伺服器）：

```bash
python scripts/evaluation.py 
  -t sse 
  -u https://example.com/mcp 
  -H "Authorization: Bearer token123" 
  -H "X-Custom-Header: value" 
  evaluation.xml
```

### 3. HTTP (串流式 HTTP)

適用於基於 HTTP 的 MCP 伺服器（您必須先啟動伺服器）：

```bash
python scripts/evaluation.py 
  -t http 
  -u https://example.com/mcp 
  -H "Authorization: Bearer token123" 
  evaluation.xml
```

## 命令列選項

```
用法: evaluation.py [-h] [-t {stdio,sse,http}] [-m MODEL] [-c COMMAND]
                     [-a ARGS [ARGS ...]] [-e ENV [ENV ...]] [-u URL]
                     [-H HEADERS [HEADERS ...]] [-o OUTPUT]
                     eval_file

位置參數:
  eval_file             評估 XML 檔案的路徑

選填參數:
  -h, --help            顯示此幫助訊息
  -t, --transport       傳輸類型: stdio, sse, 或 http (預設: stdio)
  -m, --model           使用的模型 (預設: gpt-4.1)
  -o, --output          報告的輸出檔案 (預設: 列印至標準輸出 stdout)

stdio 選項:
  -c, --command         執行 MCP 伺服器的指令 (例如 python, node)
  -a, --args            該指令的參數 (例如 server.py)
  -e, --env             格式為 KEY=VALUE 的環境變數

sse/http 選項:
  -u, --url             MCP 伺服器網址
  -H, --header          格式為 'Key: Value' 的 HTTP 標頭
```

## 輸出結果

評估腳本會生成詳細報告，包含：

- **統計摘要**：
  - 準確度（正確數/總數）
  - 平均任務耗時
  - 每個任務的平均工具調用次數
  - 總工具調用次數

- **逐項任務結果**：
  - 提示詞與預期回應
  - 代理人的實際回應
  - 答案是否正確 (✅/❌)
  - 耗時與工具調用詳情
  - 代理人對其處理方法的總結
  - 代理人對工具的回饋

### 將報告儲存至檔案

```bash
python scripts/evaluation.py 
  -t stdio 
  -c python 
  -a my_server.py 
  -o evaluation_report.md 
  evaluation.xml
```

## 完整範例工作流程

以下是建立並執行評估的完整範例：

1. **建立評估檔案** (`my_evaluation.xml`):

```xml
<evaluation>
   <qa_pair>
      <question>找出在 2024 年 1 月建立最多任務的使用者。請問其使用者名稱為何？</question>
      <answer>alice_developer</answer>
   </qa_pair>
   <qa_pair>
      <question>在 2024 年第一季合併的所有 Pull Request 中，哪一個儲存庫的數量最多？請提供儲存庫名稱。</question>
      <answer>backend-api</answer>
   </qa_pair>
   <qa_pair>
      <question>尋找在 2023 年 12 月完成且從開始到結束耗時最長的專案。請問該專案花了多少天？</question>
      <answer>127</answer>
   </qa_pair>
</evaluation>
```

2. **安裝依賴項**：

```bash
pip install -r scripts/requirements.txt
export OPENAI_API_KEY=您的金鑰
```

3. **執行評估**：

```bash
python scripts/evaluation.py 
  -t stdio 
  -c python 
  -a github_mcp_server.py 
  -e GITHUB_TOKEN=ghp_xxx 
  -o github_eval_report.md 
  my_evaluation.xml
```

4. **查看報告** (`github_eval_report.md`) 以：
   - 查看哪些問題通過或失敗。
   - 閱讀代理人對工具的回饋。
   - 識別待改進領域。
   - 對 MCP 伺服器設計進行迭代優化。

## 疑難排解

### 連線錯誤

如果遇到連線錯誤：
- **STDIO**：驗證指令與參數是否正確。
- **SSE/HTTP**：檢查 URL 是否可存取且標頭正確。
- 確保環境變數或標頭中已設定任何必要的 API 金鑰。

### 準確度低

如果許多評估失敗：
- 查看代理人對每個任務的回饋。
- 檢查工具描述是否清晰且全面。
- 驗證輸入參數是否有完整文件說明。
- 考慮工具回傳的數據量是否過多或過少。
- 確保錯誤訊息具備引導性（可執行）。

### 逾時問題

如果任務逾時：
- 使用效能更強的模型（例如 `gpt-4.1`）。
- 檢查工具是否回傳了過多數據。
- 驗證分頁功能是否正常運作。
- 考慮簡化複雜的問題。
