# 範例：決策紀錄擷取 (Decision Record Capture)

**使用者請求**： 「記錄我們決定從 REST 遷移到 GraphQL API 的決策」

## 工作流程

### 1. 從上下文中擷取決策
從對話中識別出：
- **決策事項**：將面向客戶的 API 從 REST 遷移至 GraphQL。
- **背景 (Context)**：REST 端點已變得難以維護（超過 50 個端點）。
- **替代方案**：保留 REST、嘗試 gRPC、採用 GraphQL。
- **理由 (Rationale)**：更好的用戶端體驗、型別安全、單一進入點。

### 2. 尋找決策日誌
```
Notion:notion-search
query: "架構決策" 或 "ADR"
```

找到：「架構決策紀錄 (Architecture Decision Records)」資料庫。

### 3. 獲取結構綱要 (Schema)
```
Notion:notion-fetch
```

取得屬性：決策事項 (Decision) (title), 日期, 狀態, 領域, 影響程度, 決策者, 利害關係人。

### 4. 建立決策紀錄
```
Notion:notion-create-pages
parent: { data_source_id: "decision-log-collection-id" }
pages: [{
  properties: {
    "決策事項": "遷移至 GraphQL API",
    "date:日期:start": "2025-10-16",
    "date:日期:is_datetime": 0,
    "狀態": "已接受",
    "領域": "架構",
    "影響程度": "高"
  },
  content: "[包含背景、理由、替代方案等完整內容的決策紀錄...]"
}]
```

**內容範例**：

```markdown
# 將面向客戶的 API 遷移至 GraphQL

## 背景 (Context)
我們的 REST API 已增長至 50 多個端點，且模式不一致。前端與行動團隊頻繁要求新的端點，導致：
- API 膨脹且維護負擔沉重。
- 數據的過度擷取 (Over-fetching) 或擷取不足 (Under-fetching)。
- 用戶端功能的迭代速度緩慢。
- 錯誤處理方式不一致。

## 決策 (Decision)
將面向客戶的 API 從 REST 遷移至 GraphQL，同時對內部服務維持 REST 架構。

## 理由 (Rationale)
**為什麼選擇 GraphQL**：
- 用戶端僅擷取其所需的內容（解決過度/擷取不足問題）。
- 單一進入點，具備自我描述功能的結構綱要 (Self-documenting schema)。
- 透過程式碼生成實現型別安全。
- 更好的開發者體驗 (DX)。
- 面向用戶端 API 的行業標準。

## 曾考慮的選項

### 選項 A：保留 REST (維持現狀 Status Quo)
**優點**：無遷移成本，團隊熟悉。
**缺點**：無法解決核心問題，維護成本持續增加。
**決策**：拒絕 —— 無法解決根本原因。

### 選項 B：gRPC
**優點**：效能高，強型別。
**缺點**：瀏覽器支援問題，學習曲線較陡，非針對面向用戶端的場景設計。
**決策**：拒絕 —— 較適合內部服務。

### 選項 C：GraphQL
**優點**：解決過度/擷取不足問題，極佳的 DX，強大的生態系統。
**缺點**：具備學習曲線，快取機制較複雜，需要遷移成本。
**決策**：**已接受**

## 後續影響 (Consequences)

**正面影響**：
- 前端/行動開發速度加快。
- 減輕 API 維護負擔。
- 更好的型別安全與工具支援。
- 單一進入點簡化了部署流程。

**負面影響**：
- 3-4 個月的遷移時程。
- 團隊需要培訓。
- 需要解決快取策略。
- 監控/偵錯模式發生變更。

## 實作計畫
1. 設定 GraphQL 伺服器 (Apollo Server)。
2. 舉辦結構綱要 (Schema) 設計工作坊。
3. 漸進式遷移（從新功能開始）。
4. 雙軌執行期 (Dual-run)（同時運行 REST 與 GraphQL）。
5. 棄用舊的 REST 端點。

**時程**：2025 年第四季開始，2026 年第一季完成。
**負責人**：後端團隊主管。

## 成功指標
- API 回應時間提升 30%。
- 用戶端擷取效率提升（傳輸數據量減少）。
- 新端點要求數量減少。
- 開發者滿意度評分提升。
```

### 5. 提升可發現性 (Discovery)
在「架構 Wiki」中新增連結，並在 Slack 上通知團隊。

## 關鍵成功因素
- 在背景資訊尚清晰時及時擷取決策。
- 記錄了曾考慮過的替代方案。
- 同時列出優缺點。
- 具備清晰的實作計畫。
- 儲存至決策日誌供未來參考。
- 使團隊易於發現。
